- 21 Canvas autosave (`context/feature-specs/21-canvas-autosave.md`) — implemented; not tried in a browser yet.
  - Installed `@vercel/blob` (`^2.8.2`). Needs `BLOB_READ_WRITE_TOKEN` (set in `.env.local`) in every environment.
  - Schema: unchanged — the existing `Project.canvasJsonPath` (already commented as the Blob URL) is reused. No migration. Prisma holds only the URL; the canvas JSON lives in Blob.
  - The Blob store is **private** (a first version used `access: "public"` and the store rejected it). `lib/canvas-blob.ts`: `parseCanvasSnapshot` (`{ nodes: [], edges: [] }` arrays, else `null`), `uploadCanvasSnapshot(projectId, snapshot)` (`put` to `canvases/<projectId>-<random>.json`, private, `application/json`; random suffix so no cached older copy is served), `downloadCanvasSnapshot(url)` (`get` with the store token; throws when missing or not a snapshot), `deleteCanvasSnapshot(url)` (best effort, logs on failure). `CanvasSnapshot` type added to `types/canvas.ts`.
  - API, `app/api/projects/[projectId]/canvas/route.ts`: `PUT { nodes, edges }` → upload → set `canvasJsonPath` → delete the previous blob; returns 204. `GET` → `{ canvas: null }` before the first save, else `{ canvas: { nodes, edges } }`. Both: 401 without a session, 404 for a missing project or no access (`getAccessibleProject`, so owner and collaborators — both can edit the room), 400 invalid body (`PUT`), 502 when Blob fails.
  - Autosave, `hooks/use-canvas-autosave.ts` — `useCanvasAutosave({ projectId, nodes, edges, enabled })` → `{ status, save }`, `status` = `idle | saving | saved | error`. Serializes nodes / edges without the per-client fields `useLiveblocksFlow` keeps locally (`selected`, `dragging`, `measured`, `resizing`), so selecting a node is not a change. 1500 ms debounce; skips when the body equals the last saved one; a save requested while one is in flight runs once that finishes (with the newest canvas). The canvas at the moment `enabled` turns on is the baseline (not saved). Pending changes are sent with `keepalive` on `pagehide` and on unmount.
  - Load, `hooks/use-saved-canvas.ts` — `useSavedCanvas({ projectId, nodes, edges, onLoad })` → `{ state: loading | ready | error, retry }`. Decides once, from the room as it mounted: if it had any node or edge, nothing is fetched. Otherwise `GET` the canvas and, if it has content and the room is still empty when the response arrives (nobody started drawing meanwhile), call `onLoad`. `CanvasFlow`'s `loadSnapshot` adds the nodes and edges through `onNodesChange` / `onEdgesChange` `add` changes, clears the undo history (restoring is not an undoable edit), and fits the view.
  - Autosave is `enabled` only once the load is `ready`, so an empty room is never saved over the stored snapshot. If the load fails, autosave stays off and the Save button shows the error; clicking it retries the load.
  - Save button: `components/editor/save-button.tsx` — `SaveButton`, first in the workspace navbar actions (before Templates), same outline style. Idle `Save` icon "Save", saving spinning `Loader2` "Saving…", saved `Check` (`text-success`) "Saved", error `AlertCircle` (`text-error`) "Save failed" with the reason as tooltip. Clicking saves immediately; disabled while the saved canvas loads and while saving. The navbar is outside the room, so the canvas reports `{ status, error, onSave }` up through `components/editor/canvas-save-context.tsx` (`CanvasSaveProvider` / `useCanvasSaveReporter()`, same pattern as starter templates); `EditorShell` holds it.
  - Verified: `tsc --noEmit`, `eslint`, `npm run build` pass (`/api/projects/[projectId]/canvas` in the route list); `lib/canvas-blob.ts` against the real store under `tsx`: upload → download returns the same snapshot → delete → `get` returns nothing; an unauthenticated fetch of the blob URL is 403.
  - Not verified: the route handlers over HTTP with a session or against the database; anything in a browser — the button states, autosave timing, restoring into an empty room, skipping a room with content, the `keepalive` flush.

## Architecture Decisions

- Canvas persistence: Liveblocks Storage is the live state; Vercel Blob holds the saved snapshot (`CanvasSnapshot` JSON, private store, read and written only by `lib/canvas-blob.ts`); Prisma holds only the snapshot URL in `Project.canvasJsonPath`. The snapshot is loaded into a room only when the room is empty — a room with content is never overwritten from Blob. Clients go through `/api/projects/[projectId]/canvas`, which checks project access; blob URLs never reach the browser. Requires `BLOB_READ_WRITE_TOKEN`.

- Canvas: `components/canvas/` holds the canvas surface. `CanvasRoom` is the only place that mounts `LiveblocksProvider` / `RoomProvider`, and it is rendered by the server workspace page with the project ID as room ID; Liveblocks hooks come from `@liveblocks/react/suspense`. Canvas content lives in Liveblocks Storage under `flow` and is read and written only through `useLiveblocksFlow`; node and edge shapes come from `types/canvas.ts`, which templates and AI output must also follow. New nodes are built only by `createCanvasNode()` in `lib/canvas-shapes.ts` and added through `onNodesChange` with an `add` change. The hex values in `NODE_COLORS` are the one allowed exception to the tokens-only rule (they are data stored on nodes, defined by `ui-context.md`).
- Theming: `:root` holds the ui-context tokens (`--bg-*`, `--text-*`, `--accent-*`, ...); shadcn variables (`--background`, `--primary`, ...) alias onto them, so restyling happens in `globals.css` only, never in `components/ui/*`.
- `<html>` carries the `dark` class permanently so shadcn's `dark:` variants always apply (dark-only app).
- Editor chrome is controlled: `components/editor/editor-shell.tsx` owns the project sidebar and AI sidebar open state and passes `isSidebarOpen`/`onToggleSidebar` to the navbar and `isOpen`/`onClose` to the sidebar. Each editor page renders the shell itself with the project lists it fetched; pages (unlike layouts) re-render on navigation, so the sidebar is fresh after create/delete without an extra refresh. Both sidebars are `fixed` at `top-15` to sit under the `h-12` navbar; change all three together.
- Dialogs: future dialogs compose `components/ui/dialog.tsx` directly (`DialogContent` > `DialogHeader` > `DialogTitle`/`DialogDescription`, `DialogFooter` for actions); colors come from the globals.css tokens.
- Project dialogs: all dialog/form/loading/error state and the project mutations live in `useProjectActions`; `ProjectDialogsProvider` calls it once in the editor layout, renders the three dialogs, and exposes the state through context so the sidebar and the `/editor` page open the same dialogs. Mutations go through the hook's `runMutation`. The hook holds no project list: lists are server data, re-read via `router.refresh()` or navigation. Dialogs pass `rounded-3xl` via `className` instead of editing `components/ui/dialog.tsx`.
- Project ownership in the UI comes from which list a project is in: `ownedProjects` → My Projects tab with actions, `sharedProjects` → Shared tab without actions.
- Project ID = Liveblocks room ID = workspace URL segment (`/editor/<id>`). The client builds it (`lib/workspace.ts`) and sends it as `id` on create; the server validates the format and rejects duplicates. Renaming does not change it. Server components read projects through `lib/projects.ts` and `lib/project-access.ts`, not through the API routes.
- Identity and access for server components live in `lib/project-access.ts`: pages call `requireIdentity()` first, then `getAccessibleProject()` for a single project. A missing project and a project without access are indistinguishable to the caller and both render `AccessDenied`, so project IDs cannot be probed.
- Collaborators: the database stores only `projectId` + lowercased email. Names and avatars are never persisted; `lib/collaborators.ts` reads them from Clerk on each list request. Invite and remove are owner-only and checked server-side with `checkOwnership()` (`lib/project-api.ts`) before the mutation; the UI hiding those controls for collaborators is cosmetic. The collaborator ID in the remove route is always combined with the project ID in the query.
- Feature dialogs that belong to one workspace (share) keep their state in their own hook (`hooks/use-share-dialog.ts`) and are rendered by `EditorShell`, not through `ProjectDialogsProvider`, which stays limited to create / rename / delete.
- Liveblocks: rooms are private (`defaultAccesses: []`) and created only by `POST /api/liveblocks-auth`, after the project access check. Access comes solely from the access token that route issues, scoped to the single requested room — no wildcard room permissions and no permissions stored on the room, so the database stays the only source of truth for who may enter. Server code gets the client through `getLiveblocks()` in `lib/liveblocks.ts`, never by constructing one. User name, avatar and cursor color travel in the token's `userInfo` (typed by `UserMeta` in `liveblocks.config.ts`); the color is derived from the Clerk user ID, not stored. Requires `LIVEBLOCKS_SECRET_KEY` in every environment.
- Prisma 7: CLI config is `prisma7.config.ts` (auto-detected; loads `.env` via `dotenv`, not `.env.local`), schema is the multi-file `prisma/` folder (`schema.prisma` holds generator + datasource, models live in `prisma/models/*.prisma`), client output is `app/genrated/prisma` (gitignored — run `npx prisma generate` after install; import from `@/app/genrated/prisma/client`). App code imports the client only via `lib/prisma.ts`. The Accelerate branch uses the built-in `accelerateUrl` option, so `@prisma/extension-accelerate` is not installed.
- Local database: the `prisma dev` server (`default`), started with `$env:NODE_OPTIONS='--experimental-sqlite'; npx prisma dev --name default --db-port 5432` — the flag is required on Node 22.12 (`node:sqlite` is unflagged from 22.13). It must be running for the app and for migrations. `DATABASE_URL` (in `.env` and `.env.local`) uses `127.0.0.1` and `sslmode=disable`: `localhost` resolves to `::1`, where the server does not listen, and the Prisma CLI cannot connect without `sslmode=disable`. `SHADOW_DATABASE_URL` (`.env`, wired in `prisma7.config.ts` as `shadowDatabaseUrl`) points at the server's shadow port 51215; without it `prisma migrate dev` fails because the server cannot create a separate shadow database.
- Auth: `proxy.ts` does not protect Server Action requests (`POST` + `next-action` header). Redirecting them broke Clerk's sign-out (see `context/context-issues.md`). **Every Server Function must call `await auth.protect()` itself.** `ClerkProvider` sets `afterSignOutUrl` to the sign-in URL and sign-in/sign-up fallback redirects to `/editor`.
- API auth: `proxy.ts` returns a JSON 401 for unauthenticated `/api/*` requests instead of calling `auth.protect()` (which redirects or 404s API requests). Route handlers still read `userId` from `auth()` themselves and return 401 without it; ownership failures are 403, unknown projects 404. Shared response helpers live in `lib/project-api.ts`.
- Auth: route protection is default-deny in `proxy.ts` using a plain path check against the Clerk sign-in/up env vars — not `createRouteMatcher`, which is deprecated in `@clerk/nextjs` 7. New public routes must be added to the `publicRoutes` list there. Per Clerk guidance, pages/handlers that touch protected data should still call `await auth.protect()` themselves.
- Clerk appearance: `colorBorder` and `colorNeutral` use `var(--text-primary)` because Clerk renders them at ~7–11% alpha; a dark token (e.g. `--border-default`) makes Clerk borders invisible.
- `NEXT_PUBLIC_CLERK_SIGN_IN_URL=/sign-in` and `NEXT_PUBLIC_CLERK_SIGN_UP_URL=/sign-up` were added to `.env.local` (they were missing; standard Clerk names) — set them in every deployment environment.
- `cn()` comes from the `cn` package (shadcn-ui/cn, clsx + tailwind-merge replacement) installed by the shadcn CLI; generated components import it directly, `lib/utils.ts` re-exports it for app code.
